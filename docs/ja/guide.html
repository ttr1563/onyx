技術ガイド

コマンド名ではなく、保護対象で止める。

root daemon、pinされたLinux BPF LSM、TOTP付きの範囲限定保守を組み合わせます。

実行フロー

1. 通常操作Osmanthus prefix不要
2. Kernel hook対象階層と操作
3. 判定許可・lease・拒否
4. 証跡local JSONL
5. 保守scope付きTOTP lease

processの起動自体ではなく、保護対象に対するdelete、rename、truncate、write、chmod、chownを変更前に拒否します。Pythonや別名binaryから同じfilesystem操作を行っても同じkernel境界を通ります。

保護範囲

入力動作
保護外pathOS本来の動作。
保護path＋指定action同期拒否し、監査eventを記録。
一致する有効leaseそのpath・action・接続元cgroupだけ一時許可。
保護root配下へのmount祖先関係の差替えを防ぐため拒否。
256 dentryを超える探索ELOOPでfail closed。

write境界：writeはopt-inで、write syscallと新規の書込み可能shared mappingを対象にします。既存の書込み可能mappingは取消せないため、有効化前にwriterを停止・再起動します。

daemonと障害時動作

osmanthusdがpolicy reload、TOTP検証、保守lease、session、/var/log/osmanthus/audit.jsonlを管理します。BPF map/linkは/sys/fs/bpf/osmanthusにpinされるため、daemonがcrashしても保護は外れません。監査consumer停止時はdaemonが異常終了し、systemdが再起動します。memory上の保守leaseは再起動で失効します。

同一schemaのprogram更新は全置換linkをattach・一時pinしてから正式pinへ昇格します。途中停止時は次回起動でpin状態を修復します。

shell証跡

policy monitor add UID --shell /bin/bashは元のlogin shellを保存し、そのaccountを/usr/bin/osmanthus-shellへ変更します。PTY supervisorは入出力をdaemonへ記録してから転送し、記録不能時は子processを終了します。monitor removeで元shellへ戻します。--shellを省略した場合はexec eventのみです。

PTY証跡はterminalの生入出力をbase64で記録するため、入力したsecretやapplication出力を含み得ます。自動redactは行いません。

SSM Session Managerは既定でshを起動するため、accountのlogin shellを通らない場合があります。SSM専用手順に従い、/usr/bin/osmanthus-shellを起動する制限付きSession documentを使用します。PTY統合がなくてもkernelの保護階層判定はhost全体で有効です。

policyと認証

policyとdigestは/etc/osmanthusのroot所有・read-only fileです。構造化された変更にはroot権限とpolicy管理者TOTPの両方が必要です。policy値は確認可能な設定であり、暗号化secretではありません。

sudo osmanthus policy protect add /srv/production \
  --action delete --action rename --action truncate --action write

sudo osmanthus maintenance grant \
  --path /srv/production/releases/old --action delete --for 5m

sudo osmanthus policy maintenance set --default 15m --maximum 12h
sudo osmanthus maintenance pause --path /srv/production/database --for 8h

daemonはleaseをUnix socket接続元のkernel cgroupへ固定します。別login cgroupは遮断を維持しますが、同じcgroupを共有するprocessにはleaseが適用されます。SSMやservice entry pointでは専用の一時systemd serviceを使用します。

DBと情報持ち出し

filesystemの完全性保護だけではcredential読取りやDB queryを止められません。identity別のsecret read、DB接続先、外向き通信先の制御は別の次段階とし、DB roleとDB固有auditも併用します。

担保しない範囲

Osmanthusは管理対象の非root identityを制約するものです。root、侵害されたkernel、侵害されたboot chainは封じ込めません。TOTPは独立承認ですが、物理的な本人確認の証明ではありません。Windows Server native強制backendは未実装です。
