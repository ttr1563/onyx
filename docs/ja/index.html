Linux command safety

サーバー操作に、最後の防御線を。

Osmanthusは指定階層の破壊的なファイル操作を遮断し、証跡をローカル保存し、範囲限定の保守解除にTOTPを要求します。

クイックスタート

小さな構成で、明示的に守る。

強制監視版は現在開発ブランチです。パッケージ公開前にローカルで構築・検証し、policy管理者用のRFC 6238互換認証アプリを登録します。

git clone https://github.com/ttr1563/osmanthus-shell.git
cd osmanthus-shell
git checkout feature/enforced-shell-monitoring
cargo build --release --locked
# 3 binaryとserviceを導入します。詳細は「導入」を参照。

sudo osmanthus policy init --account production-policy-admin
sudo systemctl enable --now osmanthusd
sudo osmanthus policy protect add --path /srv/production --action delete --action rename

強制フロー

通常のコマンド操作を、保護対象で判定。

  1. 観測登録UIDのexecと任意のPTY入出力を記録します。
  2. 照合カーネルで対象階層と操作種別を照合します。
  3. 拒否保護操作を対象変更前に失敗させます。
  4. 保守TOTP付きの階層・操作・cgroup限定leaseが自動失効します。

カスタムポリシー

root管理で環境固有ルールを追加。

system policyを一度初期化し、強制境界が必要なdirectoryと破壊操作だけを指定します。以後の変更にはroot権限と別管理のpolicy管理者TOTPが必要です。

sudo osmanthus policy protect add --path /srv/production \
  --action delete \
  --action rename \
  --action truncate \
  --action write

sudo osmanthus maintenance grant \
  --path /srv/production/releases/old \
  --action delete --for 5m

sudo osmanthus policy maintenance set \
  --default 15m --maximum 12h

データ境界

まず完全性を守り、アクセス制御は分離する。

opt-inのwrite保護でreleaseやcredential directoryを不変にできます。DB読取り、認証情報、外向き通信先はidentityを考慮したread・network policyが必要なため、コマンド名判定とは分けた次段階として設計します。

sudo osmanthus maintenance pause \
  --path /srv/production/database \
  --for 8h

leaseは認証した接続元のkernel cgroupへ固定され、別login cgroupは遮断を維持します。

対象外

Osmanthusが担保しない範囲。

Linux root、侵害されたkernel・boot chainは封じ込めません。TOTPは独立した承認と時間稼ぎであり、物理的な本人確認ではありません。Windows Server native版は未実装です。
