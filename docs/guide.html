Technical guide

Protection follows the resource, not the command name.

A root daemon, pinned Linux BPF LSM links, and scoped TOTP maintenance form the enforced boundary.

Runtime flow

1. Normal commandNo Osmanthus prefix
2. Kernel hookTarget ancestry + action
3. DecisionAllow, lease, or deny
4. EvidenceLocal JSONL event
5. MaintenanceScoped TOTP lease

A process may start, but a selected delete, rename, truncate, write, chmod, or chown below a protected root is rejected before the target changes. Using Python or another binary does not bypass the same kernel operation.

Scope

InputEffect
Unprotected pathNormal operating-system behavior.
Protected path + selected actionSynchronous denial and audit event.
Matching active leaseOnly that path and action are temporarily allowed.
Mount below a protected rootDenied to prevent ancestry replacement.
Path deeper than the 256-dentry walkFails closed with ELOOP.

Write boundary: write is opt-in and covers write syscalls and new writable shared mappings. Stop existing writers before activation because an already-writable mapping cannot be revoked.

Daemon and failure behavior

osmanthusd owns policy reload, TOTP verification, maintenance, sessions, and /var/log/osmanthus/audit.jsonl. BPF maps and links are pinned below /sys/fs/bpf/osmanthus, so a crash does not detach enforcement. Audit-consumer failure terminates the daemon and systemd restarts it; maintenance leases disappear on restart.

Program upgrades are blue-green: all replacement links attach and receive temporary pins before formal pins are promoted. Startup repairs an interrupted promotion.

Shell evidence

policy monitor add UID --shell /bin/bash stores the original shell and changes that account to /usr/bin/osmanthus-shell. The PTY supervisor records input and output before forwarding it and terminates the child if daemon recording fails. Removing the UID restores the original shell. Without --shell, Osmanthus records exec events only.

PTY evidence is raw base64-encoded terminal content and can contain typed secrets or application output; it is not automatically redacted.

SSM Session Manager starts sh by default and can bypass the account login shell. Use a restricted custom Session document or shell profile that executes /usr/bin/osmanthus-shell. Kernel protected-root enforcement still applies host-wide even without PTY integration.

Policy and authentication

The policy and digest are root-owned read-only files under /etc/osmanthus. Structured changes require root and the policy-administrator TOTP. Policy values are inspectable configuration, not encrypted secrets.

sudo osmanthus policy protect add /srv/production \
  --action delete --action rename --action truncate --action write

sudo osmanthus maintenance grant \
  --path /srv/production/releases/old --action delete --for 5m

sudo osmanthus policy maintenance set --default 15m --maximum 12h
sudo osmanthus maintenance pause --path /srv/production/database --for 8h

Database and exfiltration

Filesystem integrity does not stop credential reads or database queries. Identity-aware secret-read policy, database destination policy, and outbound destination control are separate planned layers. Database roles and native audit remain authoritative.

Security boundary

Osmanthus is intended to constrain managed non-root identities. It does not contain root, a compromised kernel, or a compromised boot chain. TOTP is an independent approval factor but not proof of physical presence. Native Windows Server enforcement is a separate, incomplete backend.
