Technical guide

How Onyx works.

A precise look at the decision point, one-time approval, local evidence, and the limits operators must preserve.

The protection model

Onyx v0.1 is an explicit command wrapper. Automation or an operator invokes onyx run -- <command>. Onyx evaluates the argument vector before it creates the child process. It does not intercept commands that are launched outside this wrapper.

1. Requestonyx run -- ...
2. VerifyRoot-owned system policy and digest
3. DecideAllow now or create a blocked event
4. ExecuteConsume any permit before process creation
5. AuditAppend a redacted JSONL record

Fail-closed before execution: if required state or the pre-execution audit record cannot be written safely, the protected command does not start. A completion-log failure cannot undo a command that already finished.

Approval is bound to one exact command

When a risky command is denied, Onyx hashes every argument's byte length and value in order. This preserves argument boundaries: approving one argument vector does not approve another spelling or an added option.

BlockedPending event, 10-minute lifetime
ReviewRedacted command and rules
TOTPSix digits, replay and failure checks
PermitExact digest, 30-second lifetime
ConsumedRemoved before the child starts

TOTP is a shared-secret mechanism. It provides delay when an actor lacks the enrolled authenticator, but it is not a physical-presence guarantee. Code running as the Onyx state owner, or root, can read the server-side seed. Hardware-backed asymmetric approval belongs to the planned privileged-broker design and is not claimed here.

Policy and difficult-to-interpret commands

The built-in policy covers a deliberately small set of high-risk patterns: destructive recursive deletion, filesystem formatting, raw device writes, shutdown, privilege wrappers, shell command strings, destructive find, root-wide permission changes, likely secret transfer, and decoded eval. Initialize the authoritative store with sudo onyx policy init. Structured add and remove operations then require root and an independent policy-administrator TOTP.

Onyx is not a semantic malware analyzer. Shell strings, interpreters, aliases, encoded payloads, and equivalent system calls can hide intent. Conservative rules may require approval for harmless commands, while commands outside the wrapper remain invisible.

State and local evidence

Root uses /var/lib/onyx; regular users use the XDG state directory. Directories are mode 0700 and sensitive files are mode 0600. Symlinks and unexpected file types are rejected. JSON replacement uses a same-directory temporary file, fsync, rename, and parent-directory fsync.

onyx/
├── .lock
├── audit.jsonl
├── auth-state.json
├── config.json
├── policy.json
└── events/<event-id>.json
/etc/onyx/
├── policy.json        root:root 0444
├── policy.sha256      root:root 0444
└── admin/             root-only policy TOTP and audit

The system policy is validated before every check or run. Missing pairs, unsafe type, owner or mode, invalid schema, and digest mismatch stop the operation. The digest detects inconsistency; operating-system ownership prevents a normal user from replacing both files.

Audit records contain timestamps, actions, event IDs, command digests, redacted summaries, matched rule IDs, and relevant exit status. They do not contain stdout, stderr, environment values, TOTP seeds, or submitted codes. Local evidence can still be changed by root; forward it with an existing collector when tamper-resistant retention is required.

Deployment flow

  1. Install Onyx and initialize execution state as the constrained identity.
  2. Run sudo onyx policy init and enroll the separate administrator authenticator.
  3. Verify clock synchronization, permissions, policy listing, a harmless run, and a non-executing blocked check.
  4. Change the intended automation entry point to onyx run -- ....
  5. Monitor failures and preserve both state trees before incident work.

Read the operations runbook, architecture, and security policy before production use.
