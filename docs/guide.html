Technical guide

How Onyx works.

Command evaluation, one-time approval, custom rules, and local audit records.

The protection model

Onyx v0.1 is an explicit command wrapper. Automation or an operator invokes onyx run -- <command>. Onyx evaluates the argument vector before it creates the child process. It does not intercept commands that are launched outside this wrapper.

1. Requestonyx run -- ...
2. VerifyRoot-owned system policy and digest
3. DecideAllow now or create a blocked event
4. ExecuteConsume any permit before process creation
5. AuditAppend a redacted JSONL record

Fail-closed before execution: if required state or the pre-execution audit record cannot be written safely, the protected command does not start. A completion-log failure cannot undo a command that already finished.

Safe and risky paths

FindingOnyx actionOperator result
No policy matchWrite an allowed record and start the child.The child exit code is preserved.

Approval is bound to one exact command

When a risky command is denied, Onyx hashes every argument's byte length and value in order. This preserves argument boundaries: approving one argument vector does not approve another spelling or an added option.

BlockedPending event, 10-minute lifetime
ReviewRedacted command and rules
TOTPSix digits, replay and failure checks
PermitExact digest, 30-second lifetime
ConsumedRemoved before the child starts

TOTP requires the enrolled code before approval. It does not guarantee physical presence or protect the seed from the state owner or root. Hardware-backed approval is not included in v0.1.

Add root-managed approval rules

The built-in policy covers destructive deletion, filesystem formatting, raw device writes, shutdown, privilege wrappers, shell command strings, destructive find, root-wide permission changes, likely secret transfer, and decoded eval. Initialize the authoritative system policy, then add environment-specific rules:

sudo onyx policy init --account production-policy-admin

sudo onyx policy add \
  --id production-terraform \
  --executable terraform \
  --argument-contains apply \
  --argument-contains production \
  --risk critical \
  --reason "production infrastructure change"

onyx policy list
onyx check -- terraform apply production.tfplan

sudo onyx policy remove --id production-terraform

Policy mutation requires root and the independent policy-administrator TOTP. Every supplied argument fragment must match. Custom rules add approval requirements; they cannot disable built-in rules. v0.1 does not provide an absolute, unapprovable deny mode.

{
  "schema_version": 1,
  "rules": [{
    "id": "production-terraform",
    "executable": "terraform",
    "argument_contains": ["apply", "production"],
    "risk": "critical",
    "reason": "production infrastructure change"
  }]
}

Onyx is not a semantic malware analyzer. Shell strings, interpreters, aliases, encoded payloads, and equivalent system calls can hide intent. Conservative rules may require approval for harmless commands, while commands outside the wrapper remain invisible.

State and local evidence

Root uses /var/lib/onyx; regular users use the XDG state directory. Directories are mode 0700 and state files are mode 0600. Symlinks and unexpected file types are rejected. JSON replacement uses a same-directory temporary file, fsync, rename, and parent-directory fsync.

onyx/
├── .lock
├── audit.jsonl
├── auth-state.json
├── config.json
├── policy.json
└── events/<event-id>.json
/etc/onyx/
├── policy.json        root:root 0444
├── policy.sha256      root:root 0444
└── admin/             root-only policy TOTP and audit

The readable system policy contains rule IDs, executable names, argument fragments, risk levels, and reasons; do not place credentials in rule fields. It is validated before every check or run. Missing pairs, unsafe type, owner or mode, invalid schema, and digest mismatch stop the operation. The digest detects inconsistency; operating-system ownership prevents a normal user from replacing both files.

Audit records contain timestamps, actions, event IDs, command digests, redacted summaries, matched rule IDs, and relevant exit status. They do not contain stdout, stderr, environment values, TOTP seeds, or submitted codes.

Deployment flow

  1. Install a signed RPM or Debian package, or use another documented source path, and initialize execution state as the constrained identity.
  2. Run sudo onyx policy init and enroll the separate administrator authenticator.
  3. Verify clock synchronization, permissions, policy listing, a harmless run, and a non-executing blocked check.
  4. Change the intended automation entry point to onyx run -- ....
  5. Monitor failures and preserve both state trees before incident work.

Read the operations runbook, architecture, and security policy before production use.
